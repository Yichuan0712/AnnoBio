# AnnoBio 优化引擎 v2：接口设计（草稿）

- 状态：草稿，2026-11-05，分支 `optimizer-v2`，待用户审阅后开始写代码。
- 需求见 AnnoBio-Experiments 仓库 `docs/design/paper/ANNOBIO_V2_REQUIREMENTS.md`，以下简称“需求”。
- 本文件只定接口、数据结构和与 app 的对应关系，不定具体算法参数；参数由开发先导决定。

## 1. 要解决的问题

现在同一个功能有三套互不调用的实现：

| 实现 | 位置 | 谁在用 |
|---|---|---|
| 诊断 → 聚类 → 每类一条修改 | `backend/review_pipeline.py` | app |
| Verify、片段切分加 Thompson 搜索 | 浏览器：`app/src/reviewDetailModal.js`、`reviewSuggestionOptimization.js`、`reviewSuggestionOptimizer.js`；后端只出片段和候选：`review_optimization_compositional.py` | app |
| `ReviewSession`（app 流程的复刻）和 `optimize()`（另一套自动算法） | `python/src/annobio_optimize/` | 实验 runner、H1 控制台 |

v2 只保留一个实现：Python 库里的新引擎。三处都调用它：
- app 后端；
- 实验 runner（全自动，E4/E5）；
- H1 控制台（有人介入）。

app 的界面和推送给界面的事件格式保持不变（需求 1.1、7.8）。

## 2. 分层

```
annobio_optimize.engine        纯 Python，不 import app；所有外部动作经回调
  ├─ Session                    一次优化会话：状态 + 界面上的各个操作
  ├─ Operator                   自动操作员：按固定规则调用 Session 的操作（全自动模式）
  └─ History                    跨会话的隐藏记录（可选，用户无感）

backend/annobio_engine_adapter.py   app 适配层：实现回调，把 Session 事件翻译成现有事件格式
experiments/.../methods.py:annobio  实验适配层：实现回调（计费客户端、benchmark 打分）+ Operator
runner/console.py (H1)              控制台适配层：人输入命令 → Session 操作
```

### 回调

沿用现有库的 `model` / `predict` / `evaluate` 三个回调，签名不变。

| 回调 | 作用 | app 里的实现 | 实验里的实现 |
|---|---|---|---|
| `model(request)` | 优化模型调用：诊断、提出修改、切片段、生成候选 | 现有 LLM 调用，用 Optimize 选的模型 | 计费客户端 meta 角色（Sol） |
| `predict(prompt, example)` | 用候选 prompt 跑一道题 | `llm_run_structured`，与 Run 作业相同的 schema 处理；GEPA 适配已经这样用 | 计费客户端 task 角色（Luna） |
| `evaluate(example, output)` | 打分，返回 `Evaluation(score, passed, details)` | 规则树：`score_run_gt_pairing.py`（JS 移植）；自定义代码：`/api/score/match/run` 的同一执行器 | benchmark 打分 |

引擎本身不碰数据集格式、模型供应商或评估规则，这些都在适配层。

## 3. Session：界面上的每个操作对应一个方法

| 方法 | 对应界面 | 说明 |
|---|---|---|
| `analyze()` | 点 “Optimize prompt” 后的分析 | 逐道错题生成诊断卡片；聚类；按当前阶段提出修改卡片。逐步发事件，可取消 |
| `propose(kind, …)` | 无单独按钮，由 `analyze()` 和 Operator 调用 | 生成一张修改卡片，`kind` 见第 4 节 |
| `verify(card_id)` | 点 “Click to Verify” | 只应用这一张卡片，在它针对的错题上运行，并在一组防回归题上运行（第 6 节） |
| `search(card_id)` | 点 “Optimize”（验证不通过时） | 切片段、生成候选、Thompson 搜索。结果是一张新卡片，`optimized_from` 指向原卡片，并自动验证 |
| `accept(card_id)` / `revert(card_id)` | Accept / Revert | 工作中的 prompt = 原 prompt + 全部已接受的卡片 |
| `apply()` | Apply | 返回最终 prompt 文本；app 由它生成新的 Prompt 版本 |
| `snapshot()` / `Session.restore(snapshot)` | Resume | 中断后继续；所有记录都可序列化 |
| `events()` | 进度条、卡片逐张出现 | 事件流，见第 5 节 |

规则：
- 用户能做的事，Operator 和 Agent 也只能通过这些方法做，不新增只给自动模式用的捷径（Agent 与用户同权）。
- 每个方法都写入审计记录：时间、输入、输出、花费、前后 prompt 哈希。试验记录也保存。现在 app 只返回最佳通过率，试验记录不保存，v2 补上，用于追溯。

## 4. 卡片

### 4.1 诊断卡片（Issue）

沿用现有 `Issue`，加稳定 ID，修改卡片通过 ID 引用它。现在 app 只靠自由文本 `phase1_addresses` 关联。

| 字段 | app 事件字段（`diagnosis_row.opinion.*`） |
|---|---|
| `title` | `card_title` |
| `summary` | `issue_summary` |
| `advice` | `rough_modification_opinion` |
| `category` | `problem_category_hint` |
| `reference_note` | `gt_suspect_note`（“可能是标准答案有问题”） |
| `example_id` | `input_index`、`row_indices`（适配层换算） |

### 4.2 修改卡片（Card）

所有修改都表示成“原文 → 新文”。界面只认 `old_sentence` / `new_sentence`，所以新增的几种修改都按这个形式表达，界面不用改。

| `kind` | 含义 | 原文 `old_text` | 新文 `new_text` |
|---|---|---|---|
| `replace` | 原句 → 新句（现有） | prompt 里唯一出现的一句 | 新句 |
| `insert` | 在某句之后插入新句或新段落（需求 7.2） | 锚点句 | 锚点句 + 新内容 |
| `rewrite` | 整体或整段改写（需求 7.6 的大改阶段） | 整个 prompt，或一个完整段落 | 改写后的文本 |
| `demos` | 加入例题（需求 7.1） | prompt 末段 | 末段 + `WORKED_EXAMPLES` 块（`harness.with_demos` 的同一排版） |

| 字段 | app 事件字段（`suggestions[*]`） |
|---|---|
| `id` | 前端的 `suggestion_id`；v2 由后端给出 |
| `title` | `name` |
| `rationale` | `reason` |
| `old_text` / `new_text` | `old_sentence` / `new_sentence` |
| `issue_ids` | `phase1_addresses`（适配层由 ID 填回诊断标题，保持现有显示） |
| `target_example_ids` | `target_score_row_indices`、`row_indices` |
| `cluster_id`、`cluster_label` | `issue_cluster_index`、`issue_cluster_label` |
| `optimized_from` | `optimized_from_suggestion_id` |
| `kind` | 新字段，前端可以忽略；只在详情或调试里显示 |

`demos` 卡片的理由里列出每道例题对应的诊断卡片。例题只从优化集（app 里是用户勾选参与 Optimize 的行）中选，并排除 `reference_note` 不为空的题。

## 5. 事件

后端适配层把引擎事件翻译成现有事件，前端不用改：
- `plan`
- `diagnosis_row`
- `suggestions`
- `stage`
- `error`
- `done`

Verify 和 Optimize 现在由前端自己运行，v2 改到后端。新增两个后端作业接口，形式与现有 analyze 作业相同（202 加轮询）：
- `POST /api/review/verify`
- `POST /api/review/search`

前端把原来的本地运行换成调用这两个接口，界面上的状态（Verifying… / Verified / Verification not pass / Optimizing… / “Optimized from #N”）和存储字段（`verify_states`、`verify_results`、`review_optimization_meta`）不变。这是前端代码的改动，不是界面改动。

## 6. 验证、接受与选择（需求 4、7.3、7.4）

- **目标题：** 卡片针对的错题，在应用卡片后的通过情况。与现在相同。
- **防回归题：** 不能总用同一小组题（需求第 4 节）。每次验证从“原本答对、未参与这张卡片诊断”的题中按批次轮换抽取。数量由先导决定；现在 app 是最多 2 道。
- **“超出噪声才算改进”：** 噪声幅度由先导里同一 prompt 的重复测量定下来。比较时用同一批题的配对差，不用两次独立打分的差。
- **按得分变化判断，不按全对与否（2026-11-05，先导第 0 步之后）：**
  - 第 0 步：同一 prompt 重跑 5 次。BioRED 上原本全对的摘要，有 20%–26% 下一次不再全对；而且全对的摘要很少，凑不满 4 道防回归题。按“全对与否”判断，好的修改在 BioRED 上几乎都会被拒。
  - 现在验证记录目标错题的得分增量（`target_gain`）和防回归题的得分下降（`regression_drop`）。防回归题取不在卡片目标里、原本得分最高的若干道，答对的题优先。
  - 对判对错的任务（PubMedQA、RoBBR），这和原来按对错判断完全一样。
  - 门槛（自动操作员）：
    - 卡片初筛：目标得分增量 ≥ 0.5，防回归题得分下降 ≤ 1；
    - 整批关口：16 道题配对净提升 ≥ 2，得分下降合计 ≤ 2。
    - 各门槛都不低于同 prompt 重跑噪声的 95% 分位。
  - app 界面仍按匹配行数显示通过率，不变。
- **方向与措辞（2026-11-05）：**
  - `proposals_per_cluster`（默认 1，与 app 现状相同）：每组问题让模型给出几个不同方向的改法。每个改法是一张卡片，都要验证。
  - 片段搜索只换措辞，不换方向。全自动模式下，每组问题最多搜索一张卡片：该组已有卡片通过验证时不搜；否则搜进展最大的那张。
  - `search_only_promising`（默认关）：只搜有进展的卡片，即修好了部分目标、或匹配行数增加；一点进展都没有的直接放弃。
  - 两个参数由先导比较后再定。
- **Thompson 搜索的奖励：** 目标题的通过率，扣除防回归题上的回归。现在 app 不扣回归。
- **全自动模式的接受规则（Operator）：** 目标题通过，并且防回归题上没有超出噪声的回归。有人介入时，接受与否由人决定；界面照样显示验证结果，用户仍可以手动接受任何卡片，与现在相同。
- **检查点与最终选择：** 引擎保留在位 prompt 和检查点。最终选择时，**初始 prompt 永远是候选**；成绩在噪声范围内取更短的。

### 6.0 整批关口改用下一批题（2026-11-05，先导第 2 步之后，已实现）

**发现。** 先导第 2 步的 PubMedQA 结果：
- 四种配置几乎每轮都被接受，每次在本批题上的净提升是 +2 到 +6；
- 但验证分并没有随轮数上升：配置 B 在 25% 预算时是 .72，之后掉到 .65；配置 A 一直是 .65。

原因是卡片针对本批错题而写，又在同一批题上判断，修好目标题本身就显示为提升。噪声门槛挡得住随机波动，挡不住这种“只对本批有效”的过拟合。

**做法（`OperatorConfig.gate = "next"`，默认）：**
- 第 i 轮用第 i 批题做诊断、卡片验证和片段搜索。
- 决定是否替换在位 prompt 时，用第 i+1 批题：这批题本轮的诊断和卡片都没见过，在它上面做配对比较，门槛不变。
- 第 i+1 批题上在位 prompt（或被接受的新 prompt）的预测结果，直接作为下一轮的基线，不重复预测。
- 最后一批没有下一批时，退回本批比较。
- `gate = "same"` 保留旧行为，作为对照。

**用下一批题把关之后的观察（PubMedQA 重跑）：**
- 验证分稳定在 .71–.73，不再下滑。
- 但 11–12 轮里只有 2–3 轮被采纳：新题上的真实提升大约只有 +1（16 道题），低于门槛 2。

**跟进做法（已实现，默认值不变）：**
- **`gate_batches`**：关口合并后面 k 批题，比如 k=2 就是 32 道题。门槛按合并后的题数计：
  - 净提升的噪声约按 √n 增长；
  - 下降量是单向累加，约按 n 增长，所以 32 道题时 `max_batch_drop` 约取 16 道题时的两倍。
  - 关口会去掉重复的题，也去掉本轮诊断批里出现过的题。
  - 在位 prompt 的关口预测，只有恰好覆盖下一轮那批题时才沿用。
- **`EngineConfig.search_patience`**：连续这么多次试验都没有更好的奖励，就停止搜索。
  - 0 表示不提前停，跑满 `max_trials`，也就是软件现在的行为。
  - 背景：BioRED 上片段搜索花掉了一半预算，换来的只有 1–2 轮。
- **“有希望”改按噪声判断**（`search_only_promising`）：卡片的目标题提升至少要达到 `min_fix`，才去搜索。
  - 通过/不通过的任务上，这等于以前的“至少修好一道题”。
  - 部分得分的任务上，小幅波动不再算有希望。原来在 BioRED 上，几乎每张卡片都会让目标题的分数动一点。

### 6.0b 判断用任务自己的整体指标（2026-11-06，第 4 步之后，已实现）

**发现。** BioRED 的正式指标是**合并 F1**：把所有文档的命中、误报、漏报加在一起再算 F1。引擎原来对每篇文档单独打分，然后把分数加起来，相当于在优化“每篇文档 F1 的平均”。

两者不一致的后果：只有 1–2 个关系的短文档，修好它和修好一篇有 20 个关系的长文档，在引擎眼里一样重要。第 4 步 BioRED 的测试结果说明了这一点：
- 每篇文档 F1 的平均提升了 +.067，与把关时测到的 +.084 相符，说明把关本身没有误判；
- 正式的合并 F1 只提升了 +.022；
- 准确率反而低于初始 prompt。

**做法：** `Session` 和 `Operator` 增加可选回调 `aggregate(observations)`，返回一组观测的整体分数。卡片的目标提升、搜索奖励、整批关口的净提升，都改成“题数 × 整体分数的变化”。这样单位仍然是“题”，原来的噪声门槛可以继续用。下降量（防回归）仍按每道题单独计。

不传 `aggregate` 时，整体分数就是各题分数的平均，行为与之前完全相同，软件不受影响。

**噪声复核：** 用第 0 步的原始输出（账本里的回答，不需要新的调用）重新计算 BioRED 的合并 F1 噪声，“题数 × 合并 F1 差”的 p95：
- 16 篇：1.41
- 32 篇：1.85
- 48 篇：约 1.9

与原来逐篇相加的噪声同一量级，所以门槛不用改。

### 6.0c 关口不再用选出当前 prompt 的那些题（2026-11-06，第 6 步之后，已实现）

**问题。** 预测按（prompt，题目）复用：同一个 prompt 在同一道题上只跑一次。
- 第 i 轮的关口用第 i+1、i+2 批；某个方案靠这两批上的好运胜出、被采纳。
- 第 i+1 轮的关口是第 i+2、i+3 批，第 i+2 批和上一轮重叠。在这批题上，当前 prompt 用的就是让它胜出的那份好运结果，挑战者却是新跑的。

所以采纳之后，挑战者要多跨过一截运气分。先导第 2–6 步的记录里：
- 刚采纳后的那一轮（14 轮），方案平均收益 −0.98，每轮最好方案平均 −0.13；
- 其他轮（56 轮）分别是 +0.31 和 +0.91。

**做法。** 记下选出当前 prompt 的那一轮关口用过的题。之后的关口跳过这些题，往后多读批次，补足同样的题数。没有采纳时，当前 prompt 不是靠这些题选出来的，不受影响。

**同时修正（可追溯性）：** 组合方案里，如果一张卡要改的原文已被前一张卡改掉，这张卡会被跳过，不在最终 prompt 里。原来它仍被记为"已采纳"。现在 `Session.inactive` 列出这类卡，采纳时撤回它们，决策记录里只剩真正生效的卡。prompt 文本不变。

### 6.0d 落选方案继续积累证据（挑战者）（2026-11-06 用户同意，已实现，默认关）

**发现。** 先导第 3 步里，实验框架最后挑出的 prompt 都是关口拒绝过的方案：
- PubMedQA：单条修改，关口 +1（门槛 2）。测试 .760，引擎自己采纳的是 .718。
- BioRED：单条修改，关口 +0.44。测试 .430，引擎自己采纳的是 .420。

单轮关口分不出比噪声还小的真实提升，框架靠多批题累计的分数挑对了。app 里没有框架，所以引擎自己要做到这一点。

**做法（`OperatorConfig.challengers`，0 = 关；`challenger_max_gates`，默认 4）：**
1. **入选。** 某轮没有采纳时，该轮收益为正、下降量在门槛内的落选方案成为挑战者，最多保留 `challengers` 个。它入选所在那轮关口的题记为"筛选题"：它正是因为在这些题上看起来好才被留下，所以这些题不算证据。
2. **积累。** 之后每轮关口，挑战者和当前 prompt 在同一批题上成对比较。证据只算筛选题以外的题；同一道题只算一次（预测有缓存，重复题不是新证据）。累计收益按任务的整体分数算（`set_gain`，与 6.0b 相同）。
3. **替换。** 累计收益 ≥ `min_gain` × √(题数 / 关口题数)，且累计下降 ≤ `max_batch_drop` × (题数 / 关口题数)，就有资格替换。
   - 理由：噪声随 √题数 增长，真实提升随题数增长。门槛这样设，每一次判断的误换率都和单轮关口相同；多次查看会稍微放大误换率，这是近似。
   - 同一轮里，有资格的新方案和挑战者一起比本轮关口收益，最高的胜出。
4. **淘汰。** 在至少一个关口题数的新题上累计为负，或累计到 `challenger_max_gates` 个关口题数仍未达标，就丢掉。保留的按"累计收益 / √(题数 / 关口题数)"排序。
5. **重置。** 当前 prompt 一换，所有挑战者的证据清零（它们之前是和旧的当前 prompt 比的）。挑战者胜出时，它用过的题（筛选题加证据题）都记为"选出当前 prompt 的题"，之后的关口跳过（6.0c）。

**可追溯性。** 替换记录写明是哪一轮的哪个方案，并列出它来自的卡。

**成本。** 每轮每个挑战者在关口上多跑一次。重复的题有缓存，不重复花钱。BioRED 32 篇关口约 $0.015 一次。

### 6.0e 自动模式的内核向简单改写靠拢（2026-11-06 用户决定，先导第 7 步之后）

**发现。** 第 4 步到第 7 步，BioRED 一共 7 次运行，测试分都在 .37–.41；简单改写 .439。
- 简单改写每轮约 $0.04，在 $3 内跑约 80 轮。每轮只看 4 道错题，整体重写，prompt 长到约 10K 字符。
- 我们每轮约 $0.45，只跑 7 轮。第 7 步实测：优化模型每轮 35 次调用约 $0.30，任务模型约 335 次约 $0.13。钱主要花在 16 个诊断、每类 3 个方向的局部卡片和片段搜索上。
- 改写指令原来要求"越短越好"，压住了 prompt 的增长。BioRED 上长而细的 prompt 分数高。

**用户约束。** app 里的使用方式不变：用户仍然点 Optimize prompt，看到诊断卡片和修改卡片，可以 Verify、Optimize、Accept、Revert、Apply。新内核只改变自动操作员每轮怎样使用这些操作。局部修改保留，"先大后小"保留。

**做法。** 全部由已有的操作和参数组成，不新增只给自动模式用的操作：
1. 每轮诊断当前批次的前 4 道错题（`max_failed_examples` 4），相当于用户只勾选 4 行。提案附上全部 4 道题的原始输入和输出（`max_evidence_examples` 4）。
2. 4 个诊断不超过聚类门槛（`cluster_threshold` 5），不调用聚类，每个诊断出一张局部卡片（1 个方向）。前期另出一张整体改写卡片。不做片段搜索（`search_failed_cards` 关）。
3. 调度沿用 `compete`：搜索预算用到一半之前（`coarse_budget_fraction` 0.5），每轮都出整体改写和局部卡片，由关口决定哪种胜出；之后只出局部卡片，连续 2 轮没有采纳时再出一次整体改写。"先大后小"有了规则兜底，同时前期仍由验证决定。
4. 关口放宽：下两批新题上配对净提升 ≥ 1（低于同 prompt 重跑噪声的 95% 分位），下降合计 ≤ 4。另保留 2 个挑战者（6.0d），关口拒绝的好方案仍能靠累计证据换上来。
5. 整体改写指令改为：把诊断变成明确的规则、定义、判断标准和边界情况；保留仍然成立的已有规则；只合并真正重复的内容；长度不是目标。app 以后也用这条指令（用户决定）。

**预计成本。** 优化模型每轮约 9 次调用，任务模型约 130 次。BioRED 每轮约 $0.12–0.15，$3 内约 20–25 轮。

**可追溯。** 不变：每轮记录诊断卡片、修改卡片、验证结果、关口比较和胜出的卡片种类。按轮画出胜出卡片的种类和改动字数，就能直接展示"先大后小"。

### 6.0f 把简单改写原样放进引擎，交出见过的最好版本（2026-11-06 用户决定，先导第 8 步之后）

**第 8 步的发现：**
- PubMedQA：框架挑的 prompt 测试平均 .758，与最好的零样本基线持平；引擎自己最后的 prompt 只有 .740。门槛放宽后，加规则的改动一路被采纳，prompt 从 251 字符长到 7–16K。
- BioRED r1：整体改写每次让 prompt 长约 1 万字符，最后约 32K，验证 .330，低于除 MIPROv2 外的所有基线。原因是 6.0e 的改写指令（补规则、保留所有规则、长度不是目标）。

**用户决定：** 把简单改写原样放进软件，做成可视化、可交互的版本。先让准确率追平简单改写，再只加实测证明有帮助的东西。app 的使用方式不变。

**做法：**
1. **改写指令中性化。** 和简单改写一样：用这些错题改写一次，保留任务约定、输出格式和占位符；不提长短。payload 不变：诊断卡片、4 道错题的原始输入和输出、本会话的历史。
2. **每轮只出一张整体改写卡片**（`coarse_only`），不出局部卡片，不做搜索。局部修改留到内核追平后单独检验。
3. **非劣效把关。** `min_gain` 允许为负：在下两批新题上，只要损失不超过 |min_gain|（定为 1），就接受；下降合计 ≤ 6。验证初筛也放宽：目标题不变差，4 道防回归题下降 ≤ 2。最接近简单改写的"每次都接受"，只挡住明显变差的改写。负的 `min_gain` 不能和挑战者同时用（所有不变差的方案都已被接受，没有可保留的）。
4. **交出见过的最好版本**（`OperatorConfig.final = "best_seen"`）。
   - 每个在关口新题上跑过的 prompt（历任当前 prompt 和各轮方案）都记下它在这些题上的观测。只用关口题：卡片验证跑的是它自己针对的错题，会偏向它。
   - 题数至少一个关口的 prompt 中，按整体分数选最高的，相同时取更短的。每轮更新，记在 `RoundSummary.final_prompt_id`。预算中途用完时，最近一次的选择就是答案。
   - 这就是实验框架检查点的挑法搬进引擎。第 3、7、8 步里框架挑的都比引擎最后的好（第 8 步 PubMedQA 高约 .02）。app 里没有框架，用户拿到的就是引擎交出的版本。
   - 对用户而言，等于"回到历史里表现最好的那个版本"，用户在 app 里本来就能撤回到以前的版本。
   - 默认仍是 `"last"`（交最后的当前 prompt），实验里设为 `"best_seen"`。

### 6.0g 不走偏、交出可靠的版本（2026-11-07 用户同意，先导第 9、10 步之后）

**第 9、10 步的发现：**
- 第 9 步（只出整体改写）BioRED 测试 .455 / 引擎交出 .456，两次都高于所有基线；PubMedQA 不稳定：框架挑的 .774 / .702，引擎交出的 .748 / .688。
- 第 10 步（每轮同时出局部卡片）BioRED 降到 .401 / .430：轮数从约 22 降到 13–15，prompt 长得慢。局部卡片不能每轮都和整体改写一起出。
- PubMedQA r2：前两轮各损失 1 的改写被非劣效门槛接受，之后一直没回到原始 prompt 的水平。
- "见过最好"在几十个候选、每个只有 32 道题的噪声里挑最高，挑中的是膨胀的长 prompt（winner's curse）。框架挑得对，是因为它在少数检查点之间用独立数据再挑一次。
- PubMedQA 被接受的改写大多原句全留、只往后加 2–4K 字符，251 → 31–33K 字符；BioRED 以整篇重写为主。

**做法（以第 9 步为底）：**
1. **门槛 ≥ 0**（`min_gain` 0）：在下两批新题上不变差才接受。
2. **回溯**（`OperatorConfig.rollback_z`）：每轮之后，如果之前某个被接受过的版本在关口新题上的平均逐题分数比当前版本高出 `rollback_z` 个标准误（两者都至少测过一个关口的题），当前版本换回那个版本。这相当于用户在 app 里撤回到以前的版本。用逐题分数的平均，是为了能算标准误。
3. **留出验证题交版本**（`final = "holdout"`，`holdout_batches`，`final_margin`）：最开始的 `holdout_batches` 批题留出，从不用于诊断和把关，之后批次里出现的同一道题也剔除。初始 prompt 和每个被接受过的版本都在留出题上测一次。交出的是分数与最高者相差不超过 `final_margin`（逐题单位，同 `min_gain`）的版本中最短的。候选只有被接受过的版本，比"见过最好"少得多。
4. **改写整合而不追加**（`EngineConfig.rewrite_integrate`，只在 11b 打开）：改写指令加一句"把新规则整合进已有结构，修改或替换有问题的规则，合并重叠的规则，删掉不再有用的规则，不要只是在末尾追加"。可能改变 BioRED 上整篇重写的行为，所以单独检验。

**参数（11a、11b）：** `min_gain` 0，`rollback_z` 2，`holdout_batches` 2（32 道题），`final_margin` 1。

**第 11 步结果：** PubMedQA 引擎交出的 .777（11a）/ .774（11b），高于所有基线，prompt 2.4–9.6K；BioRED .407 / .409，低于第 9 步。留出 32 篇、`final_margin` 1 对 BioRED 太宽，"差不多里取最短"交出早期较弱的版本。11a 与 11b 无明显差别。

### 6.0h 两种优化风格：简洁 / 详细，开始前自动判定（2026-11-07 用户决定，第 11 步之后）

**依据：** 第 9 步与第 11a 步只差几个设置，两种做法各在一个任务上最好：

| | PubMedQA | BioRED |
|---|---|---|
| 简洁（第 11a 步） | .777 | .407 |
| 详细（第 9 步） | .718 | .456 |

留出的题太少，软件在运行中分不清版本好坏，所以不在运行中挑规则，而是在开始前按任务性质定。用户决定实验到此为止，只加这个判定。

**做法：**
1. **一个开关 `OperatorConfig.style`**：`"fixed"`（默认，按各字段原值，兼容旧计划）、`"concise"`、`"detailed"`、`"auto"`。`concise` / `detailed` 用 `STYLE_SETTINGS` 替换 5 个字段：
   - 简洁：`min_gain` 0，`rollback_z` 2，`final` holdout，`holdout_batches` 2，`final_margin` 1；
   - 详细：`min_gain` −1，`rollback_z` 0，`final` best_seen，`holdout_batches` 0，`final_margin` 0。
   其余设置两者相同（第 9 步：只出整体改写，关口下两批，`max_batch_drop` 6 等）。
2. **自动判定（`"auto"`，`suggest_style`）**：第一轮之前，优化模型看原始 prompt 和第三批里的 2 道训练题（输入与参考答案，过长截断；前两批在简洁风格下会被留出，所以不用），判断这个任务做好是靠一个简短清楚的 prompt 就能传达的判断（简洁），还是要很多任务特有的约定（详细）。问 3 次，3 次都说详细才用详细，否则用简洁（意见不一致说明任务在中间，用默认）。无法解析的回答算没投票。判定结果、每次的回答和理由记录在 `OperatorResult.style`（`StyleChoice`）。
3. **app 里**：这是开始优化前的"建议模式"卡片，用户可以接受或改成另一种（`"concise"` / `"detailed"`）；Agent 与用户能做的一样。app 默认用自动判定。
4. **论文**：全自动条件（E4）一律用 `"auto"` 的判定，人改只出现在 app 和有人参与的实验（H1）里。判定指令在正式阶段前定死，不按任务调；PubMedQA、BioRED 的正确答案已知，只算检查；RoBBR 没有预跑，它的判定是真正的检验，判成什么都照用。另一种风格的分数（第 9 步、第 11a 步）作为对照报告。

### 6.0i 简洁风格采纳过改写就不交回原始 prompt（2026-11-07 用户决定，正式运行之后）

**问题：** 正式 PubMedQA r3（自动判定为简洁）17 轮里采纳过改写，但留出的 32 题上没有版本比原始 prompt 多对 1 题以上；原始 prompt 最短，"差不多里取最短"每轮都把它交回，测试 = M0（.702）。

**做法：** `OperatorConfig.final_excludes_initial`（默认关，兼容旧计划）：`final` holdout 时，只要有别的版本在留出题上打过分，原始 prompt 就不参加挑选，在采纳过的版本里取留出分在 `final_margin` 内最短的。简洁风格打开，详细风格不变（best_seen 不受影响）。只改交出哪个版本，优化过程本身不变，所以已有运行可以按记录原样回放重算。

**论文：** 这是看过正式测试分之后的修改（10.35 的规则），所有简洁风格的运行一视同仁按新规则重算，旧规则的分数一并报告。

### 6.0j 加例子后，整篇改写不再碰例子块（2026-11-07，准备 AnnoBio few-shot）

**问题：** 正式设置只做整篇改写（`coarse_only`）。"加例子"卡片被采纳后，例子块接在 prompt 末尾；之后的改写卡片把整个 prompt（含例子块）交给优化模型重写，例子可能被改写、删掉或重新生成。RoBBR 一个例子就是一整篇论文，优化模型根本输出不下。

**做法（6.0j）：** 操作器记住被采纳的例子块（卡片新增的那段，`Session.kept_tail`）。之后的改写只把块前面的指令交给优化模型，结果后面原样接回例子块。零例子运行没有块，请求和以前逐字相同。回溯到加例子之前的版本时，那个版本不以该块结尾，改写照常处理整篇。

### 6.0k 例子只在最后加（2026-11-07 用户建议）

**理由：** 每轮都提"加例子"时，例子一旦被采纳，之后每次打分都要多带几篇例题（RoBBR 一个例子约一篇论文，同预算下轮数约减半）。只在最后加，指令优化几乎用满预算，例子只花最后一小笔。

**做法：** `OperatorConfig.demos_stage`："rounds"（默认，每轮在采纳前提出）或 "end"。"end" 时，已花比例加上目前最贵一轮的花费达到 1 − `demos_reserve` 就停止改写（再跑一轮普通回合就会吃进预留；RoBBR 一轮约占预算 10–15%），在操作器此刻会交出的 prompt（`result.final`）上做一轮只有例子卡片的回合：诊断、挑例子（每类失败一道，带参考答案）、在其余失败题上验证、下一批（`gate_batches`）上把关，规则与普通回合相同（风格的 `min_gain`、`max_batch_drop`）。通过就交出带例子的版本，否则交出原来的；运行到此结束（`stop_reason` "demos stage done"，回合 `phase` "demos"）。预留的预算花在这一轮里，总花费不超过上限。

### 6.1 提案：门槛自动校准（2026-11-05，待实现；第 2 步之后再做）

**问题。** 现在的 4 个门槛来自先导第 0 步的专门测量：3 个 prompt × 5 次重跑，花了 $0.98。门槛取决于任务、模型和批次大小。app 用户不会去做这种测量；换任务或换模型时，固定门槛要么太松（把噪声当进步），要么太严（什么都不接受）。

**做法：每轮顺便测一次噪声，门槛随数据自动定。**

1. **重跑一次。** 每轮开始时，在位 prompt 在本批题上除了正常的基线运行，再多跑一次，得到每道题两次结果的差 `d_i = s2_i − s1_i`。
   - 它们是同一个 prompt 的两次结果，差异纯粹来自噪声。
   - 这次重跑还有第二个用处：基线改用两次的平均。候选和在位 prompt 配对比较时，在位一方的噪声减半。
2. **积累噪声样本。** 每轮的 `d_i` 加进一个噪声池：
   - 全自动模式：跨轮积累；
   - app 里：同一个 Prompt 节点跨次积累，作为隐藏状态，用户无感，符合需求 1.3。

   池里按题目第一次得分高低分成两组：高分题（用于防回归门槛）和低分题（用于修复门槛）。
3. **由噪声池算门槛。** 用自助法（bootstrap）从池里抽样，模拟“候选和在位其实一样好”时会看到的差别，取它的 1−α 分位作为门槛：

   | 门槛 | 模拟的是 |
   |---|---|
   | `min_gain` | 整批 n 道题的配对净差 |
   | `max_batch_drop` | 整批题得分下降部分的合计 |
   | `min_fix` | 卡片目标题（低分题）的得分增量 |
   | `max_drop` | 防回归题（高分题）的得分下降 |

   - 对用户只剩**一个旋钮 α**（多保守），默认 0.05。
4. **样本少时不乱放。** 噪声池小的时候估计不稳，比如 PubMedQA 一批 16 道题可能一道都没翻转，估出来的噪声是 0。所以：
   - 门槛 = max（自助法估计，保底值）；
   - 保底值来自通用的先验噪声，并随池子变大逐渐让位给实测值，例如按池中题数加权。
   - 开发期实测的第 0 步数据可以作为实验里的先验，但 app 不依赖它。

**代价。** 每轮多跑 n 道题的预测，不调用 Sol。诊断（每道错题一次 Sol 调用）才是每轮的大头，按冒烟的数字，多出来的花费约占每轮的 5%–15%。

**要验证的事（先导或 E5）：**
- 自动门槛和第 0 步测出的固定门槛是否接近：同一批数据上两种都算，直接对比；
- 在 E5 里加一组对照：固定门槛 vs 自动校准，看对准确率、回归率和花费的影响。

**论文。** “按实测噪声自动设定接受门槛”可作为单独的贡献。正式写进论文前，要先查文献确认 prompt 优化领域有没有同类做法，比如统计检验式的接受规则或序贯检验。

## 7. 阶段：先大改，后小改（需求 7.6）

- 由 `Session` 的 `phase` 状态决定 `analyze()` 提出哪类卡片：
  - `coarse` 阶段：`rewrite` 卡片；
  - `fine` 阶段：`replace` / `insert` 卡片。
  - `demos` 卡片在开关打开时，于诊断后提出一次。
- **默认模式 `compete`：由验证决定大改还是小改（用户决定，2026-11-05）。**
  - 每轮都提局部卡片。
  - 整体改写卡片：在搜索预算用到 `coarse_budget_fraction` 之前，每轮都提；之后只在连续 `coarse_patience` 轮没有任何改动被采纳时才提，而且每 `coarse_patience` 轮最多提一次（卡住时再整体整理一次）。
  - 两类卡片都在同一批题上验证。通过的卡片组成几个方案：整体改写、全部局部卡片、最好的一张局部卡片。每个方案都放到整批题上，和当前 prompt 做配对比较，从合格的方案里取提升最大的，相同时取更短的。
- `coarse_to_fine`：按时间单向切换。先只大改，连续若干轮没被采纳，或者用掉设定比例的预算后，转为只小改，不再回头。
- E5 消融只改模式开关，算法其余部分相同：
  - `coarse_only`：只大改；
  - `fine_only`：只小改；
  - `coarse_to_fine`：按时间切换；
  - `compete`：由验证决定，即新版本身。
- 参数（`coarse_patience`、`coarse_budget_fraction`、`min_gain`、`max_lost`）由先导决定。
- app 里，阶段对用户不可见：用户看到的仍是一组卡片，其中前期可能出现一张整体改写卡片。

## 8. 隐藏历史（需求 1.3、7.3 吸收 OPRO）

- **会话内：** 提出新卡片时，模型能看到本会话里以前试过的卡片、验证结果和是否被接受，避免重复失败的方向。
- **跨会话（可选，默认关闭，先导决定是否打开）：** 同一 prompt 节点以前的会话记录，作为提示材料。实验中每个单元都从空历史开始，保证各重复互相独立。

## 9. 实验需要的钩子

- 每次模型调用都经过 `model` / `predict` 回调，由适配层计费和限额；引擎不自己发请求。
- 种子：所有随机选择用会话种子派生，可复现。
- 轮次：每完成一次“诊断 → 卡片 → 决定”调用 `on_round`，供调度器记录 rounds.json 和检查点。
- E5：可以导出、导入冻结的候选池（同一批卡片和片段候选），三种模式在同一池上运行。

## 10. 迁移顺序

1. 库：`annobio_optimize.engine` 加 Operator，配离线测试（固定模型响应）。不花钱。
2. 实验适配：runner 的 `annobio` 方法改用 Session 加 Operator；H1 控制台改用 Session。离线演练。不花钱。
3. 开发先导（上限 $35，每次开跑前问用户），定参数，冻结。
4. 第二期运行。
5. app：
   - 后端加适配层和 verify/search 作业接口；
   - 前端把本地 Verify 和 Optimize 换成调用后端；
   - 删除 `review_pipeline.py` 里被取代的逻辑和浏览器端搜索，或只留兼容层；
   - 库里旧的 `ReviewSession` 复刻和 `optimize()` 一并移除。
6. app 回归检查：界面、卡片字段、状态与改动前一致（截图对比加事件字段对比）。

## 11. 已知差异与待核实

- 片段和候选的生成调用，现在 app 用的是 Generate 节点的模型凭据（`reviewSuggestionOptimizer.js:51`），不是 Optimize 选的模型。**v2 所有优化步骤统一用 Optimize 模型（用户决定，2026-11-05）**，与实验一致。界面不变，费用可能改变。
- GEPA 适配里的 `_run_task_prompt` 对表格输出只取第一行。v2 的 `predict` 要按 Run 作业的完整行为处理多行输出，再交给打分。
- 规则树打分的 Python 移植要和 JS 版逐项对齐（嵌入相似度、概念 ID 匹配需要预取映射），迁移时用同一批样例做对拍。
- “每次最多错题数”（默认 30）、“最多试验次数”（默认 40）两个设置项保留，含义不变；引擎新增的参数（阶段切换、防回归题数、噪声幅度）不暴露为设置项。
