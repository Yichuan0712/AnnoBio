# AnnoBio v2 功能设计

日期：2026-10-15  
状态：提案，待讨论；不代表现有实现或已经确定的开发承诺。  
目标用户：需要导入文献、设计提示词、批量标注、人工整理并评估结果的研究人员。  
设计范围：新版工作区、节点、执行、结果、历史及相关功能。本文先确定用户行为与产品规则，不规定数据库、API 或前端框架。

## 1. 产品目标

让用户搭建工作流后，可以逐步试验、批量执行、修改、接着执行，并清楚知道每个结果来自哪里。

用户日常只需理解三个概念：

1. **步骤**：对数据做什么。
2. **结果**：某个步骤实际产出的数据。
3. **历史**：之前做过什么，以及当时的配置和结果。

产品应当让用户随时回答：

- 这个步骤当前使用哪份输入和结果？
- 哪些结果仍适用于当前配置，哪些需要更新？
- 点击运行后，究竟会执行哪些步骤？
- 已经完成的工作是否会保留？

关键承诺：手动执行与整条执行共享同一种结果；修改不会删除已有结果；执行范围和费用来源在开始前可见；历史记录保留真实来源。

## 2. 核心模型

### 2.1 工作区

一个工作区包含当前画布、步骤配置、数据集版本以及每个步骤当前采用的结果引用。

- 用户可以随时修改和保存。
- 一个步骤当前只采用一个配置版本。
- 同时比较两种方案时，可以复制步骤建立两条分支。
- 一张画布允许存在多个不相连的工作流；全局运行需要明确选中其中一个工作流，不默认执行整张画布。
- 首版一个工作区同一时间只允许一个执行任务；可以在运行期间编辑，但不能在该工作区再启动第二个任务。

这里的“工作流”指一组通过数据依赖相连的步骤及入口数据集，不另要求用户维护一份重复的流程定义。

### 2.2 结果

结果是一份实际执行得到的记录，包含输出及其来源。

- 已提交结果不可原地修改；重新运行产生新结果。
- 结果记录输入数据版本、上游结果、配置、模型、时间、状态和可获得的用量信息。
- 一个 Process 的多个输出端口属于同一次结果，分别引用其中的表。
- 单节点运行和整条运行产生相同的结果对象。
- 当前工作区显式采用一份结果；系统不从全部历史中偷偷替换成另一份。
- 部分结果可供预览，但默认不作为成功结果流向下游。

“可用”只表示结果与当前执行条件相符且完整可读取，不表示内容已经通过科学验证或人工审核。

### 2.3 执行记录

每次点击开始，都保存一次执行记录，记录当时的定义、输入、目标、使用的已有结果、实际执行的步骤与结果。

一次执行可以使用多次历史中的成果，不要求所有上游来自同一次整条运行。

开始时冻结执行计划；后续画布编辑不会改变已经开始的任务。执行记录引用实际采用的结果，不把复用伪装为重新计算。

## 3. 画布与节点

### 3.1 首版节点

| 节点 | 用途 | 主要配置 | 输出 |
| --- | --- | --- | --- |
| Dataset 数据集 | 导入、编辑、固定数据，作为流程输入 | 表格、列类型、文件、数据版本 | 数据表 |
| LLM 步骤 | 分类、抽取、整理等模型任务 | Prompt、模型、输入映射、输出 schema、生成参数 | 结构化表 |
| Process 步骤 | 使用 Python 处理、过滤、合并数据 | 代码、命名输入、输出端口 | 一张或多张表 |
| Evaluate 步骤 | 对结果进行规则或代码评估 | 预测数据、标准答案、匹配规则或代码 | 汇总指标与逐条明细 |

**LLM 步骤合并现有 Prompt 与 Run 的用户职责。** Prompt 是步骤配置，Run 是执行动作和历史记录；不要求用户先建 Prompt 节点再建 Run 节点。

抽样是数据集操作，优化是 LLM/Evaluate 的操作入口，见第 12 节。

### 3.2 连线

- 实线只表示实际数据依赖：来源步骤的输出端口，连接到下游的命名输入端口。
- 一个输入端口只连接一个来源；合并多份数据必须使用明确的多个输入。
- 连接必须形成 DAG；禁止循环，连接时提示具体冲突。
- Process 支持分支和汇合；汇合步骤只有在全部必需输入可用时才能执行。
- 评估的预测数据和标准答案都属于真实输入依赖。
- Prompt 版本、历史来源、优化建议不画成执行依赖线；在相应面板中查看。

首版 Process 的输出端口必须能被明确声明或识别。动态端口在确认实际结构前不能被假定存在；旧连接失效时显示错误，不静默删除或改接。

### 3.3 节点信息

折叠节点显示：名称、类型、结果是否适用、结果行数；正在执行时另显示任务进度。

点击节点后，侧栏提供：

- **配置**：当前编辑内容与配置版本。
- **结果**：当前采用的结果、输入摘要、输出预览及来源。
- **历史**：该步骤以前的结果与比较入口。

结果状态和任务状态分别显示。例如，“有可用结果”可以与“本次重新运行失败”同时存在，失败不覆盖以前的成功结果。

## 4. 运行操作

### 4.1 两个主入口

| 操作 | 目标范围 | 上游处理 | 下游处理 |
| --- | --- | --- | --- |
| 运行到这里 | 当前步骤 | 使用可用结果，补做缺失或需要更新的依赖 | 不执行 |
| 运行工作流 | 当前工作流所有末端步骤 | 使用可用结果，补做缺失或需要更新的依赖 | 运行至各个末端 |

末端是该工作流中没有数据消费者的可执行步骤。画布上的其他工作流不受影响。

两个入口使用同一套规划和执行机制。对每个目标，反向解析必需依赖：

1. 当前采用的结果适用，则引用该结果。
2. 结果不存在、需要更新或不可读取，则安排执行该步骤。
3. 为需要执行的步骤解析其全部必需输入。
4. 形成无关分支不会进入的执行计划。

如果所有目标都有适用结果，显示“结果已是最新，本次无需执行”，不再次调用模型。

### 4.2 重新运行

次要菜单提供：

- **重新运行此步**：强制执行当前步骤；上游按普通规则处理，下游不执行。
- **全部重新运行**：强制执行当前工作流的全部可执行步骤；入口数据仍使用当前选定的数据版本。

重新运行 LLM 是产生另一次模型输出的明确入口。即使配置相同，也可以有多份不同结果。

强制重跑成功后，新结果成为当前采用结果，其下游标为需要更新。强制重跑失败时，保留原采用结果，同时明确显示本次失败。

首版不提供含糊的“从这里开始”、任意跳过节点或默认绕过数据转换的操作。

### 4.3 运行前展示

运行前在侧栏显示计划，并在画布上高亮范围：

```text
目标：评估
使用已有结果：抽取关系（结果 #12）
将执行：标准化名称、评估
输入：文献集 v3，共 1,000 行
```

- 必需补跑的上游必须列入计划，不能隐藏在“运行一个节点”的按钮后面。
- 缺凭据、缺输入、错误连线、缺输出端口等阻止开始，并定位到具体步骤。
- 显示已知输入行数、模型和调用量估计；动态分支、表格扩展导致数量未知时明确显示未知，不给出虚假的精确费用。
- 用户在该计划上点击开始；不逐个节点重复确认。
- 配置或输入变化后重新生成计划。开始提交必须对应用户看到的计划版本，不能静默换成另一份。

## 5. 结果复用与更新

### 5.1 首版复用规则

默认只检查当前工作区已经采用的结果。满足以下条件才直接使用：

- 结果完整成功，数据仍存在且能够读取。
- 输入数据集版本一致。
- 每个输入绑定的上游结果 ID、输出端口和输入别名一致。
- 影响输出的配置一致，包括 Prompt、映射、schema、模型身份、生成参数、代码及可追踪的执行环境。

有效设置在开始时解析并冻结。修改全局默认设置后，需要判断它是否改变了该步骤实际使用的设置。

模型身份与登录凭据分开。仅轮换 API key 不应使结果过期；改变模型、服务地址或会影响行为的提供方设置需要更新。

复用是一种明确使用已有观察结果的行为，不承诺再次调用随机模型或外部服务会得到相同内容。

### 5.2 修改影响

| 修改 | 对结果的影响 |
| --- | --- |
| 节点名称、位置、颜色、备注 | 不影响 |
| Prompt、输出 schema、输入映射 | 当前步骤及依赖它的下游需要更新 |
| 模型或生成参数 | 当前步骤及下游需要更新 |
| Python 代码或执行环境 | 当前步骤及下游需要更新 |
| 数据集内容、类型、行顺序或选用版本 | 所有读取它的步骤及其下游需要更新 |
| 改接输入或输出端口 | 受影响的消费者及其下游需要更新 |
| 在末端新增步骤 | 已有结果保留，仅新步骤缺少结果 |
| 新增无关分支 | 已有分支不受影响 |

首版以数据集版本和步骤结果为判断单位，不做列级依赖推断或跨版本逐行缓存。

上游重新运行后产生新结果 ID，即使内容相同，下游也需要更新。首版优先保持来源语义清楚。

修改只标记需要更新，不自动运行，不删除旧输出。如果修改被撤销，原采用结果重新满足条件时可以恢复为可用，无需重跑。

### 5.3 结果状态

| 状态 | 展示与行为 |
| --- | --- |
| 无结果 | 提示运行；规划时可补做依赖 |
| 可用 | 可直接作为下游输入 |
| 需要更新 | 旧结果可查看，并解释差异；普通运行会重算 |
| 部分结果 | 可查看完成行和错误；默认不供下游使用 |
| 数据不可用 | 结果记录存在但文件缺失等；解释原因，不能冒充成功缓存 |

## 6. 固定数据与人工介入

### 6.1 从任意结果创建数据集

成功结果和历史结果提供“创建数据集”；多输出步骤先选择端口。

- 创建独立、固定的数据集版本。
- 保留来源结果、输出端口和创建时间。
- 上游以后改变时，这份固定数据不会被自动更新。
- 界面明确显示“固定数据，来自某次结果”；不要求它与当前上游保持一致。
- 底层可以引用不可变数据，产品操作不要求复制整份大表。

可提供快捷操作“用这份结果继续”，完成创建数据集并引导连接下一步；原有连接不被静默改接。

```mermaid
flowchart LR
    A[旧实验的 C 结果] -. 创建固定数据集 .-> S[固定数据集]
    S --> D[新步骤 D]
    D --> E[新步骤 E]
```

图中的虚线只说明来源，不是运行时依赖。实际画布默认只显示数据集到 D、E 的数据线。

### 6.2 人工修改

模型结果不能原地编辑。用户选择“创建数据集并编辑”，修正后得到新的数据版本，再连接下游。

导入中间结果、人工注入数据、保留旧实验输出都使用这一入口，避免引入另一套临时覆盖机制。

### 6.3 数据版本

- 数据集导入、抽样、显式刷新外部来源或保存内容编辑，会形成可追踪的新版本。
- 编辑期间可有未保存草稿；开始执行前必须明确保存并冻结版本。
- 历史执行继续引用原版本，后续编辑不会改写过去。
- 外部检索的返回数据导入后是一份固定观察；获取最新数据通过“刷新来源”显式产生新版本。

第一版不做自动人工审批节点。人工检查后创建或确认固定数据，再启动后续步骤；审批等待、多人分派和超时另列后续功能。

## 7. 暂停、失败与恢复

### 7.1 执行状态

界面区分未开始、运行中、暂停中、已暂停、成功、部分失败、失败和已取消。服务中断后显示“已中断，可恢复”。

- **暂停**：不再安排新的计算，保存已完成进度，之后可恢复。
- **取消**：结束本次任务并保留已有成果；想继续时创建新任务，使用已完成的成功结果。
- **恢复**：继续同一次任务的冻结定义和输入，重试未完成部分。

恢复会新增执行尝试，沿用成功步骤和已保存的行 checkpoint；已经提交的失败或部分结果不原地改写，补做完成后提交新的结果 ID，并保留此前尝试的记录。

已经发出的模型请求可能无法撤回。迟到返回不能把已取消任务改为成功，也不能覆盖另一份结果。

### 7.2 节点和分支失败

- 一个步骤失败，仅阻断依赖它的下游。
- 不依赖该失败步骤的其他分支继续完成。
- 汇合步骤的任一必需输入失败时，显示“等待失败输入恢复”，不使用缺了一支的数据执行。
- 任务结束后清楚显示成功、失败和受阻步骤；部分失败不能显示为整条成功。

### 7.3 批量行恢复

- LLM 步骤按输入行保存成功输出、错误及进度。
- 暂停、失败或服务重启后，恢复同一冻结任务，只补未完成或失败行。
- 一行扩展为多行时，仍以原始输入行作为 checkpoint 单位，避免重复追加结果。
- Process 首版按整个步骤重试，不承诺对任意 Python 代码做逐行恢复或只执行一次外部副作用。
- 部分数据默认不能流向下游。用户确实需要成功部分时，显式“将成功行创建为数据集”，保留失败和排除数量。

“补做同一任务失败行”与“修改 Prompt 后重新跑剩余行”不是同一操作。修改配置后创建新任务；首版不自动拼接不同配置下的逐行结果。

## 8. 运行期间编辑与撤销

- 开始后，任务使用冻结的配置、输入版本和结果引用。
- 运行期间允许编辑画布，但新配置只影响后续任务。
- 节点在运行期间被修改，任务完成后的结果进入历史；只有执行条件仍匹配当前工作时，才自动成为当前采用结果。
- 没有发生语义变化的独立分支结果可以正常采用，不因为另一处修改而全部拒绝。
- 任务恢复前明确显示“继续运行开始时的版本”，不偷偷读取当前编辑内容。
- 撤销/重做只改变编辑内容和显式结果选择，不删除真实执行记录，不撤销已经发生的模型调用。

## 9. 历史、版本与实验比较

### 9.1 节点历史

每份结果展示时间、输入版本、配置摘要、模型、状态、行数及可获得的成本信息。

- “查看”只打开历史预览，不改变当前结果或下游输入。
- “采用此结果”必须显式点击，且结果与当前输入和配置兼容。
- 不兼容的结果提供差异说明，以及“创建数据集”或“基于所属执行继续”的入口。
- 改变采用结果后，下游按来源变化标为需要更新。

### 9.2 工作流历史

每次开始形成一条记录，展示目标、冻结画布、执行步骤、复用步骤、结果、错误与进度。

- 查看历史进入独立只读视图，不改当前工作区。
- “基于此次记录继续”创建工作副本，保留原定义及原结果引用；失败或未完成结果仍标为不可供下游使用。
- 工作副本不会自动补跑，需要用户点击运行。
- 用户可以命名副本，例如“关系抽取方案 B”，首版不要求维护复杂的分支树。

### 9.3 结果比较

首版支持两份结果并排查看，比较 Prompt/模型/配置差异、指标及输出变化。

只有输入身份可对齐时才提供逐行差异。输入不同、排序或聚合无法对齐时明确说明，不按当前表格行号强行配对。由行身份和来源映射支持后续更复杂的比较。

## 10. 界面布局

- **顶部**：工作区名称、保存状态、当前工作流、运行工作流、执行状态、历史。
- **中央画布**：数据流、结果状态、执行范围高亮。
- **右侧检查面板**：配置、结果、节点历史、运行计划；提供“运行到这里”。
- **底部任务面板**：本次任务进度、失败原因、暂停/恢复/取消、技术日志。

历史预览有明确的只读标识及返回当前工作的入口；不把旧画布直接覆盖到正在编辑的画布。

运行记录被引用的数据或媒体不可直接删除。删除动作要先展示引用范围；首版不实现自动清理正在被工作区、数据集或历史引用的成果。

## 11. 用户场景验收

| 编号 | 场景 | 预期行为 |
| --- | --- | --- |
| S01 | A→B→C→D 从未执行 | 运行工作流，按依赖得到全部结果 |
| S02 | 手动执行了 A、B，再运行工作流 | 使用手动结果，仅执行 C、D |
| S03 | 已完成 A→B→C，新增 D、E | 原结果仍可用，仅执行 D、E |
| S04 | 运行到 C | 只处理 C 及其必要上游，D 不执行 |
| S05 | 目标上游缺结果 | 计划列出补跑步骤，开始后按依赖执行 |
| S06 | 修改 B 的 Prompt | A 保持可用；B 及下游需要更新，旧结果可查看 |
| S07 | 改变模型或有效生成参数 | 相应步骤及下游需要更新 |
| S08 | 修改名称、颜色或位置 | 结果保持可用 |
| S09 | 相同配置想再生成一次 | 重新运行此步，产生独立新结果 |
| S10 | 一条分支失败 | 独立分支继续；失败分支下游受阻，任务不显示整条成功 |
| S11 | 两支汇合但一支没有成功结果 | 汇合步骤不启动，并指出缺失输入 |
| S12 | 1,000 行中 12 行失败 | 显示 988 成功、12 失败；同任务恢复仅补失败或未完成行 |
| S13 | 暂停或服务重启 | 已完成成果保留；恢复原任务定义和输入 |
| S14 | 运行时修改 Prompt | 活动任务不变；旧配置结果保存在历史，不冒充新配置结果 |
| S15 | 用旧 C 结果接新 D | 创建固定数据集连接 D，保留真实来源 |
| S16 | 人工修正输出后继续 | 创建并编辑数据集，以新数据版本执行下游 |
| S17 | 查看旧执行 | 只读查看，不改变当前工作 |
| S18 | 从旧实验开始另一方案 | 创建工作副本，原实验保持可查看 |
| S19 | 重新运行失败，但以前有成功结果 | 保留原结果，同时显示新失败；不静默覆盖 |
| S20 | 输入数据版本变化 | 依赖它的步骤需要更新，无关工作流不受影响 |
| S21 | 所有结果仍适用时点击运行 | 提示无需执行，不再次调用模型 |
| S22 | 撤销一次配置修改 | 不丢执行记录；原采用结果满足条件时恢复可用 |
| S23 | 改接输入或删除已连接输出端口 | 提示受影响步骤，不能沿用旧输入结果 |
| S24 | 恢复途中配置已修改 | 明确恢复冻结版本；要运行新配置则另建任务 |

## 12. 相关功能的新入口

### 12.1 数据导入与抽样

- 保留 CSV、Excel、文本、图片、PDF 以及生物医学来源导入能力。
- 导入操作得到 Dataset；来源查询及刷新记录查询参数、时间和来源。
- 数据集菜单提供“创建样本”：随机、分层、指定行等具体方式按实际支持展示。
- 样本保存源数据版本、抽样设置、实际选择的行身份及随机种子（适用时）。
- 再次抽样创建新的数据集；不覆盖已有样本，不因后续源表编辑改变旧样本。
- 训练/验证/测试划分保存各自数据身份，评估和优化明确显示使用哪一份，避免无意混用。

### 12.2 评估

Evaluate 是读取明确数据输入的普通可执行步骤，参与相同的计划、复用、历史和来源追踪。

- 支持规则匹配、分组规则及自定义代码。
- 汇总指标和逐条明细属于同一结果。
- 标准答案版本、匹配方式、排除行范围变化时，评估需要更新。
- 被排除或未匹配的行数可见，不仅展示一个总分。

### 12.3 提示词优化

优化从 LLM 或 Evaluate 面板发起，创建独立的优化任务，明确使用的基线、训练/验证数据与预算。

- 产出候选 Prompt/配置版本及证据，不覆盖当前采用的 Prompt。
- 用户可以比较、试跑并显式采用候选；采用后依照普通规则更新结果适用性。
- 优化产生的内部试验保留来源，不把其中某次高分结果自动当作当前工作流结果。
- 优化不形成画布循环；优化方法及高级配置在专门面板中提供。

### 12.4 Agent

Agent 使用与界面完全相同的配置、执行计划、结果选择和历史能力。

- 修改提案显示影响范围；运行请求显示将执行与将复用的步骤。
- 用户已在执行卡片确认的完整计划，不逐步重复确认。
- 编辑或计划变化后，过期执行卡片不能静默启动另一份计划。
- 取消、恢复、创建固定数据集和采用候选均调用同一产品操作。
- 不绕过结果适用性检查，不擅自把部分结果或旧配置结果接入下游。

### 12.5 导出与分享

区分两种用户意图：

- **分享工作流定义**：当前配置、连接、输入说明和输出说明；凭据只保留待填写的绑定，不包含 API key。
- **分享实验成果**：明确选择数据、结果、历史及图片/PDF 是否随包携带，并保留来源。

Python 项目导出默认表达所选工作流的完整计算定义，不因本地恰好有缓存而悄悄省略步骤。若从固定数据集继续，则该数据集是明确入口。导出不承诺具备桌面端全部历史交互。

## 13. 首版范围与后续功能

这里的优先级用于组织新版实现，不表示立即删除现有功能。旧能力在新入口可用前是否保留，需要实施计划另行说明。

| 阶段 | 内容 |
| --- | --- |
| P0：完成执行闭环 | 新工作区与基础节点、版本化数据、统一结果、两种运行入口、明确计划、复用/更新、暂停恢复、分支失败、节点/工作流历史、从历史创建工作副本、固定数据集、核心评估、文本与媒体读取 |
| P1：完成研究工作流 | 丰富导入与抽样入口、结果比较、工作副本管理、提示词优化迁移、Agent 全部入口对齐、Python 导出与项目分享 |
| P2：依据需求扩展 | 任意子图运行、审批节点、多人协作、并发执行、跨工作区缓存、列级或增量行级重算、历史分支树与自动存储清理 |

P0 必须通过第 11 节场景验收，工作副本先提供基本的创建与打开能力。更丰富的副本管理及结果比较放在 P1；不能把缺少入口描述为功能已经交付。

## 14. 实现必须保持的约束

以下约束是产品一致性所需，不限定具体存储方案：

1. 配置定义、当前结果选择、执行进度、已提交结果分别管理；画布缓存不是结果的唯一来源。
2. 一个稳定结果 ID 对应一份不可变已提交结果；运行中的 checkpoint 单独保存。
3. 一个结果能追到每个实际输入，覆盖多输入、多输出、抽样、人工修改及标准答案。
4. 执行计划冻结后不读取实时画布决定剩余输入。
5. 复用规则由共享逻辑决定，界面、Agent、单步骤与整条执行不能各算一套。
6. 恢复需要配置记录和实际数据均可读取；缺少文件或媒体资源时明确报错，不伪装可恢复。
7. 删除、撤销、另存、移动项目文件不能意外改写或丢失已引用的成果；项目身份不能仅依赖当前绝对路径。
8. 成本、模型响应和外部副作用按实际可观察情况记录；不承诺取消后一定零费用或故障恢复后外部调用只发生一次。

## 16. 后续讨论时优先验证

本文已经为这些问题给出默认方案，讨论时可调整，不要求先解决所有高级能力：

1. 用“运行到这里”表达可能补做上游，是否比“运行节点”更符合目标用户理解？
2. LLM 合并 Prompt/Run 后，内部版本与显式比较分支能否覆盖常见提示词实验？
3. 把旧输出和人工修正统一转成 Dataset，实际操作是否足够顺畅？
4. 普通运行默认复用、重新运行显式强制，用户是否能从计划和按钮清楚区分？
5. 历史只读查看与工作副本继续，是否能满足用户保存、比较和延续实验的需求？

下一步应以一张小型示例工作流验证这些交互：两条分支、一次汇合、一个评估步骤，依次演示手动执行、修改、扩展、失败恢复和旧结果继续。通过后再编写数据模型与实施计划。
