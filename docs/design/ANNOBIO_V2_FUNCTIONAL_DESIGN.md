# AnnoBio v2 功能设计

日期：2026-10-16（取代 2026-10-15 的初稿）
状态：讨论稿。第 1–5 节是讨论中已经同意的方向，第 7 节记录已定的问题。按模型设置的部分已经做完（第 3.4 节）。

本文先讲新的思想，再讲要加哪些功能、删哪些东西。初稿里讨论后决定不做或暂缓的内容，列在第 6 节。

## 1. 核心思想

**只有一套运行方式：点运行时，自动算出要跑哪些步骤；没变的步骤直接用已有结果，变了的才重跑。**

由此得到几条规则：

1. **跑过的结果都留着。** 每次运行都在节点的 History 里新增一条记录，不覆盖旧的。
2. **没变就不重跑。** 一个步骤的 Prompt、输入、列映射、代码都和已有结果对得上，就直接用这份结果，不再调用模型。
3. **变了就标"需要更新"，不隐藏。** 节点继续显示上一次的结果，并标明它已经过期；旧结果可以看，但不能再给下游当输入。
4. **跑之前先告诉你。** 会跑哪些步骤、用哪些已有结果、读哪些数据、大概多少行，确认后才开始。
5. **断了接着跑。** 失败或停止以后，再点一次运行，完成的步骤自动跳过，停在一半的 Run 从断的那一行继续。
6. **每次运行留一条运行记录。** 跑了什么、复用了什么、哪里失败，都能回头查。

用户只需要理解三样东西：**步骤**（对数据做什么）、**结果**（某个步骤实际产出的数据）、**运行记录**（某次点运行做了什么）。

## 2. 和现在的区别

| | 现在 | 新版 |
|---|---|---|
| 运行方式 | 两套：节点窗口的 Run 只跑这一步；Current Pipeline 的 Run Pipeline 每次从头跑整条 | 一套："运行到这里"自动补跑缺结果的上游 |
| 上游没结果时 | 下游按钮变灰，显示 "Waiting for upstream" | 仍然可以点，弹出计划，连同上游一起跑 |
| 已有结果 | 单步会用；整条运行一律重跑 | 都会用，不重复调用模型 |
| 输入改了以后 | 节点显示"没有结果"，旧结果只能去 History 找 | 节点显示旧结果，标"需要更新" |
| 运行前 | 整条运行只列出读外部 Dataset 的步骤，没有行数和调用量 | 给出完整计划 |
| 运行记录 | 只有整条运行有，在 Pipeline 卡片的 Run History 里，只读 | 每次运行都有，放在底部面板的"运行记录"页签 |
| 选模型 | 只能用 Settings 的默认模型 | 新建 Run、发起 Optimize 时可以选（已完成） |

## 3. 要加的功能

### 3.1 运行到这里

**入口**

- Run / Process 窗口里的 Run 按钮，样子不变。上游都有当前结果时，照旧直接只跑这一步；上游缺结果时，点了先弹出计划。
- 节点右键菜单加"运行到这里"，效果相同。
- 想跑整条，就在最后一个节点上点。
- 只有 Run 和 Process 有"运行到这里"。Evaluate 和 Optimize 不算在 Pipeline 里，照旧用各自窗口里的按钮。

**算出要跑哪些步骤**

从目标节点出发，沿连线往上游找，经过的每个 Run 和 Process：

- 有当前结果（History 里签名对得上，而且已完成）：直接用。
- 没有当前结果，或结果已过期：安排它跑。上游一旦要跑，下游的签名会跟着变，所以下游自然也会被安排进去。
- 碰到的 Dataset 就是输入。每个输入口只接一条线，所以找到的结果是唯一的，不需要再选路线。

输入不一定都在开头。多个 Dataset 接同一个 Process，或者中间的步骤再接一张对照表，都只是"上游有几个 Dataset"，不需要特别处理：

```
文献集 ──→ 抽取 ──→ 整理 ──→ 打分
     物种对照表 ──↗
```

想换输入，就在画布上把另一个 Dataset 拖到入口，和现在一样。

**运行前的计划**

只有要跑的步骤不止一个时才弹出；只跑一步时直接开始，和现在一样：

```
运行到：打分
输入：文献集（1,000 行）→ 抽取
      物种对照表（50 行）→ 整理
使用已有结果：抽取（#12）
将执行：整理 → 打分
模型：打分用 claude-sonnet；调用次数未知（取决于整理输出几行）
                                          [取消] [开始]
```

能算出来的行数和调用次数就写上；经过 Process 或一行输出多行以后算不出来，就写"未知"，不给一个假的准确数字。缺凭据、缺列映射、连线有错时不能开始，并指出是哪个节点。

**执行**

- 按顺序调用现在单步运行用的函数（Run 窗口和 Process 窗口里 Run 按钮背后的那两个），前一步完成再开始下一步。Agent 的 `run_nodes` 已经是这样一步步跑的，两者共用同一段代码。
- 每一步的结果照旧写进各自节点的 History，格式不变。
- 运行期间，计划里的节点全部锁住，不能改，保证后面的步骤用的就是确认计划时的配置。

**失败、停止、继续**

- 某一步失败（整步没跑成，例如凭据无效、Process 代码报错）：不再开始依赖它的步骤，已经完成的结果都留着。
- Run 有个别行出错不算这一步失败：出错的行照常传给下游，和现在单步运行一样（第 7 节已定第 1 条）。
- Stop：停掉当前这一步，后面的不开始。
- Resume：就是再运行一次。完成的步骤已有结果，自动跳过；停在一半的 Run 从断的那一行接着跑。不需要另外保存"运行到了哪里"。

### 3.2 "需要更新"的显示

- 节点的输入变了（改了 Process 代码、换了上游结果、改了列映射、改接了输入），签名就对不上了。现在的做法是清掉节点上的结果，改为继续显示上一次的结果，并在节点和窗口上标"需要更新"。
- 过期的结果只能看，不能给下游当输入。下游显示"上游需要更新"，运行到这里时会先重跑上游。
- 签名自动匹配照旧：把输入改回原样，旧结果自动重新成为当前结果，不会重跑。

### 3.3 运行记录页签

- 底部面板的页签变成：Current Pipeline | Prompt Version | **Executions** | Log（Log 只在桌面版有）。英文名不用 Runs，因为 Process 的运行也记在这里。
- 每次点"开始"新增一条：时间、目标节点、复用了哪些步骤、跑了哪些步骤、每一步的状态和出错行数。点一步可以在画布上定位到那个节点。
- 正在跑的那条有 Stop；失败或停止的那条有 Resume。
- 记录跟着项目保存（和节点 History 存在一起），复制、另存、导出项目时一起带走。

### 3.4 按模型选择和设置（已完成，2026-10-15/16）

- Prompt 窗口的 Create Run 和 Evaluate 窗口的 Optimize prompt 左边各有一个模型下拉框，只列测试通过的模型。新建的 Run / Optimize 记住选中的模型。
- 每个 Optimize 记住自己用的模型，Evaluate 换模型不会让已有 Optimize 的结果消失。
- Settings 的三个页签改名为 Run / Optimize / Agent。页顶选中哪个模型，下面的 Max tokens、Concurrency、Context window 就是哪个模型的值；保存时选中的模型就是默认模型。

详见 [NODE_MODEL_REVIEW.md](NODE_MODEL_REVIEW.md) §4 的更新。

## 4. 要删的东西

已于 2026-10-16 删除（[RUN_TO_HERE_PLAN.md](RUN_TO_HERE_PLAN.md) 第 6 步）。Agent 的只读工具 `get_pipeline_runs` 也一起删了，否则就成了只有 Agent 能看整条运行历史。

| 删什么 | 原因 | 前提 |
|---|---|---|
| Pipeline 卡片上的 Run Pipeline、Stop、Resume 按钮 | 由"运行到这里"代替 | "运行到这里"先上线 |
| Pipeline 卡片上的 Run History 按钮和窗口 | 由"运行记录"页签代替 | 运行记录页签先上线 |
| Run Pipeline 弹出的 "Prepare inputs for this run" 窗口（`pipelineRunDialog.js`） | 输入由连线决定，计划里列出 | 同上 |
| Agent `pipeline_action` 的 run / stop / resume | 用户没有这个入口了，Agent 也不能有；改为 `run_nodes` 指定目标节点 | 同上 |

保留：

- Current Pipeline 面板和 Export Python Project。删掉运行按钮以后，这个面板只剩选路线和导出两个用处，以后是否改成"导出到这里"、去掉这个面板，另议。
- 后端 Pipeline Runner 暂时不删，导出仍然用它的编译器。界面不再用它运行。

## 5. 保持不变

- **节点 History**：每个 Run / Process 一份记录列表、按输入算签名、记录之间互相引用、选一条旧记录时上游跟着切、删除时连带删下游，都不变。
- **存储**：网页版每条记录一个文件，桌面版存在 `.yc` 里。
- **Prompt 和 Run 仍是两个节点**，Prompt 版本、Optimize 的 Apply、Prompt Version 面板都不变。
- **Sample、Evaluate、Optimize 仍是画布上的节点。**
- **"Generate again"**：已完成的 Run 想用同样的配置再生成一次，仍在窗口里点它，产生一条新记录。

## 6. 初稿里不做或暂缓的内容

| 初稿内容 | 决定 | 原因 |
|---|---|---|
| Prompt 和 Run 合并成一个"LLM 步骤" | 不做 | 版本、Apply、Prompt Version 面板都要重做；"一个 Prompt 给样本和全量各接一个 Run"会变成两份 Prompt 文本 |
| 节点"显式采用"一份结果，不自动匹配 | 不做 | 自动匹配让改回原样时旧结果自动回来，不用重跑花钱，History 也几乎不用改 |
| Sample、Optimize 不再是节点 | 不做 | 现在的用法没问题，改了收益不大 |
| 一个工作区同时只能有一个运行任务 | 不做 | 现在单步之间可以并行，没必要退步 |
| 单步和整条运行的结果合成一份存储 | 暂缓 | "运行到这里"走单步函数，结果本来就只存在节点 History，暂时不需要 |
| 关掉 app 后运行在后端继续 | 暂缓 | 需要改用后端 Runner，工作量大；第一版接受关掉 app 就停（第 7 节已定第 3 条） |
| Dataset 版本、工作副本、并排比较两份结果、审批节点 | 暂缓 | 与运行无关，以后单独讨论 |
| 一条分支失败时，不相关的分支继续跑 | 暂缓 | 第一版按顺序跑，失败就不再开始依赖它的步骤 |

## 7. 已定

**已定（2026-10-16）**

1. **出错的行照常往下传。** Run 有个别行出错，这一步仍算完成，下游照常运行；出错的行在输出列里是错误信息，下游窗口不另外提示（2026-10-16 起去掉了原来的"上游有 N 行出错"提示）；出错行数在上游 Run 自己的结果和运行记录里看。这和现在单步运行的规则相同，两种运行方式不分开定。只有整步失败时，下游才不开始。
2. **只跑一步时不弹计划，按钮也不变。** 只有要连同上游一起跑时才弹出计划。
3. **关掉 app 运行就停。** 和现在单步一样，重新打开后再运行一次就接着跑。
4. **Evaluate 和 Optimize 不算在 Pipeline 里**，不参与运行到这里。
5. **以前的整条运行记录不搬进新的运行记录页签。** 2026-10-08 以后的整条运行，结果在结束时已经导入各节点的 History，删掉 Run History 窗口不会丢结果。更早的运行如果没导入过，界面上就看不到了；后端文件留在原处，不删。
6. **Agent 新建 Run、发起 Optimize 时可以选模型**，不传就用 Settings 里选中的模型。
7. **用过的 Prompt 和 Dataset 继续锁定。** 想改就新建版本或复制一份，再把线接过去。每个版本都是画布上看得见的节点，Prompt Version 面板照常可用。所以"需要更新"只来自：Process 改了代码、上游换了结果、Run 改了列映射、改接了输入。
8. **不加"只重试出错的行"。** 出错的行算已处理；想补就用 Generate again 整个重跑。

目前没有待定问题。

## 8. 实施顺序

每步单独提交，带测试。每一步要读的代码、要改的文件和函数、测试和验收标准，见 [RUN_TO_HERE_PLAN.md](RUN_TO_HERE_PLAN.md)。

| 步骤 | 内容 | 用户能看到的变化 |
|---|---|---|
| 1 | 规划函数：给定目标节点，算出复用哪些、跑哪些、读哪些输入、估计行数；纯函数加测试 | 无 |
| 2 | 执行：按计划依次调用单步运行，锁住计划里的节点，处理失败、Stop、再次运行；Agent 的 `run_nodes` 改用同一段代码 | 无 |
| 3 | 入口和计划窗口：Run 按钮的 "Run with upstream"、右键"运行到这里"、计划确认框 | 可以连同上游一起跑 |
| 4 | 运行记录页签：保存、列表、Stop / Resume、定位节点 | 每次运行都有记录 |
| 5 | "需要更新"的显示 | 改了输入不再看不到旧结果 |
| 6 | 删除第 4 节列出的按钮、窗口和 Agent 操作；更新 Guide 和 Agent 说明 | Pipeline 卡片只剩导出 |
